# Claude subscription provider

`ClaudeCodeProvider` uses each user's unmodified official Claude Code executable.
The official client owns sign-in, credential storage, renewal and provider policy.
The harness does not collect subscription tokens. Anthropic documents this use in
its [product integration terms](https://code.claude.com/docs/en/legal-and-compliance)
and [subscription SDK guidance](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan).

## Host setup

Install a current official Claude Code release that supports the flags in the
[CLI reference](https://code.claude.com/docs/en/cli-reference). Configure its
executable path as one program, without shell arguments. Missing or unsupported
client features fail the request.
Use an absolute executable path or a bare PATH name. Relative paths containing
a directory are rejected because host authentication and inference may use
different working directories.

Hosts share `resolve_claude_code_program(configured: Option<&Path>) -> PathBuf`
from `ejm-harness-auth`. It preserves an explicit override. Otherwise it checks
the user's `.local/bin/claude` on Unix or `.local/bin/claude.exe` on Windows,
then uses maintained native PATH lookup. Home lookup uses Rust's standard
[`std::env::home_dir`](https://doc.rust-lang.org/std/env/fn.home_dir.html) rather
than another directory package. The pinned Rust version uses `USERPROFILE` or
the native profile directory on Windows, and `HOME` or the account database on
Unix. This does not establish native Windows runtime acceptance. Automatic Windows lookup accepts
`claude.exe`, so a batch shim cannot precede the native executable. Missing
clients keep the native command name and fail through the normal launch error.
Resolve a relative override against the host working directory before passing
it to auth and inference, so both select the same executable.

Use `ClaudeCodeClient` from `ejm-harness-auth` for official sign-in, status and
sign-out. Before selecting the provider, call `status(cancel).await` and
`require_subscription()` on its result. API-key and third-party routes fail that
check so selecting a subscription does not silently select different billing.
Known environment authentication and routing overrides are removed from the
status and inference processes. Do not pass subscription credentials to an HTTP
adapter.

Construct `ClaudeCodeProvider::new(config, executor)` with an `Executor` that
uses `harness.governor()`, then select it through `harness.configure_provider`.
Include the safe account identity, selected model and executable identity in the
host's stable nonsecret binding. A provider change clears foreign opaque state
through the existing provider-selection contract.

`ClaudeCodeConfig` exposes `program: PathBuf`, `cwd: PathBuf`, `model: String`,
`timeout_ms: u64` and `reservation: Reservation`. The host should provide a
dedicated runtime directory for `cwd`. Defaults use the shared client resolver,
the current directory, model `sonnet`, a 120-second deadline, and reservations
of 256 MiB memory, eight processes and 256 KiB output. The shared governor still
controls admission and can reject these estimates or clamp the lifetime.
Output reservations must be positive and no larger than 1 MiB.

The constructor validates configuration without launching a process. It does not
authenticate the client or make a paid request. Before every inference, the
provider runs `claude auth status --json` through the supplied executor. Status
and inference run sequentially with separate leases and the same session ID.
Both share the harness governor.

Status uses the provider's executable, working directory and resource reservation,
with its timeout capped at 15 seconds and output reservation capped at 32 KiB
(at most 16 KiB per stream). The auth crate's allowlisted parser must confirm subscription
authentication before model launch. Failed, cancelled, timed-out or truncated
status checks stop the request. A later change to an API-key or cloud source also
stops it. Hosts own account controls.

## Conversation and tools

Each model step starts a fresh supervised `claude --print` process with
`--output-format json` and a Draft-07 response schema generated by `schemars`.
The [programmatic interface](https://code.claude.com/docs/en/headless) and
[structured output contract](https://code.claude.com/docs/en/agent-sdk/structured-outputs)
define the result envelope. The adapter validates it again with `jsonschema`
and decodes JSON with Serde.

Host system instructions, ordered readable messages, tool definitions, tool
errors and artifact references travel over private stdin, limited to 8 MiB.
They do not enter process arguments. Foreign provider continuation is omitted.
The harness retains conversation history; native Claude session persistence
is disabled.

The response contains canonical assistant text and tool proposals. Each proposal
has an allowed tool name and a JSON string of arguments. The adapter decodes the
arguments and assigns a unique call ID. The existing harness loop owns grant and
argument validation, effect admission, tool execution and durable evidence.
Returning a proposal runs no harness tool by itself.

The adapter disables Claude's ordinary built-in tools, MCP servers, cloud
connectors, skills, plugins and other customizations. It supplies empty MCP
configuration, safe/restricted modes and `disableAllHooks` settings. It never
uses a permission bypass.

## Bounds and native limits

Native execution is not a security sandbox. Managed Claude policy remains
effective. Managed hooks and policy commands may run in the official client;
ordinary settings cannot override them. These are external client behavior,
separate from the harness tool grants. See the
[hooks reference](https://code.claude.com/docs/en/hooks) and
[settings precedence](https://code.claude.com/docs/en/settings).

The shared executor retains its command lease through process cleanup, including
cancellation and dropped callers. It tracks queued and running status checks, so
cancellation and `wait_idle()` cover their cleanup. Its documented native
capability limits still apply. Stdin is excluded from serialized command requests
and executor artifacts. Bounded client output can enter the executor's retained
output artifacts.

On Windows, auth and inference children join a kill-on-close Job before their
code runs. Cleanup retains the Job until membership confirms no descendants
remain. Unix captured commands use their own process group. Interactive sign-in
keeps inherited terminal stdio and, on Unix, the terminal's foreground group;
cancellation reaps that direct client. Hosts must suspend their terminal reader
and restore it only after the auth operation finishes. Keep the host's Tokio
runtime alive through cleanup. See [native process support](native-process-support.md)
for package selection, nested-Job errors, and native verification limits.

The auth supervisor retires a captured Unix group's numeric identity only after
group termination and child reaping succeed, before awaiting output-reader
cleanup. Pending waits and cleanup errors keep ownership armed. This prevents a
later completed-owner drop from signalling an unrelated group after identifier
reuse; Windows Job ownership is unchanged.

The provider rejects process failures, cancellation, timeouts, truncated output,
unsuccessful result envelopes, missing structured output, invalid JSON and schema
mismatches. Errors omit raw client output. Replies allow at most 64 KiB of UTF-8
text and 16 tool proposals, with 64 KiB of argument JSON per proposal, within the
configured total output budget.

The adapter permits four client turns, one API retry and two structured-output
attempts, with the shared deadline as the final lifetime bound. This can involve
more than one remote model request. Usage comes from the client's cumulative
result metadata once. Input totals include ordinary input, cache writes and
cache reads; cache reads remain a reported subset of input.

See [SDK usage accounting](https://code.claude.com/docs/en/agent-sdk/cost-tracking)
and [Anthropic's input-token breakdown](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#tracking-cache-performance)
for the reported counters.

Text is emitted once after the complete reply passes validation. This route has
process startup overhead and no token-by-token streaming. Offline fixtures cover
the adapter contract without signing in or calling a paid model. They do not
establish successful inference with a live subscription or every client release.
The installed native Claude Code 2.1.303 accepted the planned options together
with `--help` on macOS. That offline check validates option parsing only.
