Availability

These APIs are prepared for source review. This guide does not announce a package release, native platform certification or live service. Source checks and local previews do not prove that this page has been deployed.

Key service setup

The vault key stays in macOS Keychain, Windows Credential Manager or an unlocked Linux Secret Service in the current user's D-Bus session. Linux development builds require pkg-config and D-Bus development headers. Debian and Ubuntu use the packages pkg-config and libdbus-1-dev.

Headless Linux users must provision and unlock a user Secret Service. Missing or locked key services return an error. The harness never writes an unprotected key beside the vault or changes to plaintext storage. Hosts can offer explicit FileStore::memory() or SecretVault::memory(); these do not persist or import credentials.

Vault APIs and limits

FileStore::open(path) remains the provider-state entry point and adapts the encrypted vault. Generic host secrets use SecretVault::open(path) with SecretId::new(product, purpose, identity). Include the account and normalized origin in the identity where needed. Products can share the implementation while using separate physical vaults.

lock(cancel).await returns an exclusive transaction. Use get, set, delete, migrated and mark_migrated as needed, then call commit explicitly. Dropping without commit does not save mutations. VaultKeyStore supplies an injected protected-key boundary for hosts and offline fixtures. Synchronous lock_blocking and registry operations belong off an async or UI event thread.

Async lock acquisition stops on cancellation or after 30 seconds from the initial request, including native key access. An already-started OS key call cannot be stopped: its worker keeps the stable file lock until it returns and checks cancellation and the deadline before later changes or transaction delivery. A cancelled first key save may still finish; preserve its bootstrap marker so retry reuses that key. Runtime shutdown can wait for the native call. Synchronous lock_blocking cannot interrupt OS key calls and belongs off async and UI event threads.

Provider state is limited to 1 MiB and 64 registrations. The vault permits 128 generic secrets of 16 KiB each, 128 permanent migration markers, 4 MiB total plaintext and 8 MiB encrypted input. Corrupt, substituted, unsupported or oversized state fails before credentials become available.

Migration and recovery

A valid private legacy provider state.json migrates under its existing stable .lock. The store commits and reopens encrypted state before publishing a nonsecret version barrier that old readers reject. Preserve that barrier and lock. A completed migration refuses stale plaintext snapshots and missing ciphertext.

Registry sessions use save_registry_token, load_registry_token and delete_registry_token with the exact registry origin. The encrypted store lives under the package root's credentials directory. Legacy plaintext is never an automatic fallback.

Stop older registry clients before calling migrate_registry_token(root, origin, true). The CLI's source implementation offers ejm-cli package migrate-credentials --old-clients-stopped. An unconfirmed handoff fails before source changes. Migration verifies privacy and origin, commits a permanent destination marker, reopens encrypted state and then retires the source. Retry interrupted cleanup; logout and replacement retain the marker so stale credentials cannot return.

When key access fails, preserve the vault and unlock or restore the original OS key record. Do not delete ciphertext, barriers or bootstrap markers to suppress an error. Missing or replaced keys never trigger an automatic reset. This version has no passphrase recovery, cloud sync or portable backup format. Moving a vault changes its authenticated path identity.

Use trusted local storage. Unix files require private owner permissions; macOS extended allow ACLs are refused. Windows uses protected native ACL and handle APIs. Native Windows acceptance remains pending. OS-user protection does not isolate arbitrary code running as the same user or prevent replay of an entire valid older vault. Deleting a legacy file does not erase snapshots or storage hardware.

Official Claude Code access

Install an unmodified official Claude Code client separately. resolve_claude_code_program preserves an explicit executable override, then checks the user's native installation and PATH. Use an absolute executable path or a bare program name. Automatic Windows discovery selects claude.exe.

ClaudeCodeClient delegates sign-in, bounded status and sign-out to the official client. It never extracts subscription tokens. Suspend the host's terminal reader before interactive sign-in and restore it after the operation finishes. Sign-in has a ten-minute deadline; captured status and sign-out use fifteen seconds. Cancellation and dropped callers retain child cleanup ownership. Successful captured Unix cleanup retires its numeric group identity after termination and child reaping, before later output-drain waits. Pending cleanup and errors retain ownership; Windows Job behavior is unchanged.

ClaudeCodeProvider::new(config, executor) uses the harness's shared executor governor. Before each inference it requires the official client's subscription source, clears known API-key and routing overrides and rejects other billing sources. CLAUDE_CONFIG_DIR, when set, must be absolute. Existing Anthropic and OpenAI-compatible API-key routes remain separate.

Readable conversation, system instructions and tool definitions travel over private stdin, capped at 8 MiB. The provider disables ordinary native tools, MCP tools, customizations and session persistence. Managed provider policy can still run hooks. Native execution is not a sandbox. The harness validates proposed tools through its normal grant and execution loop.

The adapter emits text after the complete structured reply passes validation. It has process startup cost and no token streaming. Output allows at most 64 KiB of text and sixteen tool proposals within a configured total budget of at most 1 MiB. Failed, cancelled, timed-out, malformed or truncated results stop the request without exposing raw output.

Provider changes between turns

Harness::with_optional_provider lets a host open before sign-in. A missing provider rejects a submitted turn before journaling its prompt. configure_provider(provider, binding).await changes or removes the shared provider only while all managed work and queues are idle.

The host supplies a stable, nonsecret binding of 1 to 1024 printable UTF-8 bytes covering provider, account, model and endpoint. A changed binding atomically removes opaque continuation while retaining readable history and tool evidence. The same binding preserves continuation across restart. Failed validation or persistence leaves the previous configuration intact.

Exact run completion for hosts

The prepared source API Harness::subscribe_run(session_id, run_id).await returns a handle only for that exact current run, including a successor started by the local queue. None means absent or superseded, not successful completion. Use durable replay for old results.

RunHandle is clonable. Its wait includes durable completion and bounded run-end observers; a journaled RunFinished event or session Idle can arrive earlier. Clones share completion and cancellation. Dropping a handle does not cancel work. Use wait_completion to obtain RunCompletion with its summary and atomic queued_successor decision. Discard dependent prompts when that flag is true, even if the successor already finished. A false flag is not proof of current idleness. Summary-only wait stays compatible. Bound retained handles and recheck the current target, revocation and expiry after waiting outside a host's admission lock. This additive API still needs its fresh local gate, hosted review, protected publication and consumer adoption; this source page does not prove live publication.
