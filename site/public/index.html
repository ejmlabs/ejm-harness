engine

ejm-harness runs a hundred agents.

A reusable Rust engine for coding agents. Sessions that wait on a model own no shell and no thread, and every command, tool and child agent is admitted, bounded and journaled.

Build from source Embed in Rust

how it works

The engine keeps the hard parts.

Run many sessions through one resource governor, keep a durable event journal, and extend the engine from Rust, TypeScript or Python.

Waiting costs nothing

A session awaiting a model holds no process. Sessions are light state that share one provider, tool registry, store and governor.

One governor for all work

Commands reserve CPU, memory, processes and output before they start. Model requests and local jobs have separate limits, and a model cannot raise them.

Fair queues

Requests rotate between sessions, first in first out within each. A dropped waiter leaves at once, and a lease frees every reservation when it ends.

Journal first, never replay

A bounded SQLite journal records every event. After a crash, the engine recovers the run and never repeats an effect whose outcome is uncertain.

Native file tools

Read, list, search, write and patch without spawning a shell. Shell access is optional and keeps normal Bash semantics when granted.

Guarantees stated plainly

Each restriction is reported as enforced, monitored or unsupported. Native execution runs as you and is not a sandbox.

embed in rust

One harness owns the provider, tools, governor and journal.

During source development, depend on crates/ejm-harness from your own Cargo project. Add ejm-harness-coding when your host needs the standard coding tools.

Runs offline, with no account.

The replay provider replies with Demo: Hello and makes no network calls. Real provider credentials stay host configuration. 

use std::sync::Arc;
use ejm_harness::{Harness, HarnessConfig, ReplayProvider, SessionOptions};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let harness = Harness::new(
        HarnessConfig::default(),
        Arc::new(ReplayProvider::echo()),
        vec![],
    )?;
    let session = harness.create_session(SessionOptions {
        cwd: std::env::current_dir()?,
        title: "First agent".into(),
    }).await?;
    let mut run = harness.start(&session.id, "Hello".into()).await?;
    println!("{}", run.wait().await?.text);
    harness.shutdown().await?;
    Ok(())
}

sdks

TypeScript and Python share one worker.

Both SDKs share one persistent Rust worker across their sessions. There is no Node or Python dependency for Rust hosts or ejm-cli.

Custom tools stay ordinary functions.

Tools are plain functions in your language, with schema validation, progress and cooperative cancellation. Credentials travel over stdin, never through arguments.

async with AsyncHarness(
    config={"provider": {"kind": "echo"}}
) as harness:
    session = await harness.create_session(
        title="First agent"
    )
    run = await session.start("Hello")
    async for event in run:
        if event["type"] == "text_delta":
            print(event["text"], end="")

footprint

Light by design.

Agent capacity, model capacity and local job capacity are separate. A hundred waiting agents share a small pool of local work instead of a shell each.

note

Measured on 18 October 2026 on a Mac16,8 with 12 logical CPUs and 24 GiB RAM, using deterministic provider responses. A hundred sessions each ran three Bash checks; sampled engine resident memory was 25.72 MiB and sampled peak local jobs was 4. A modern Mac does not prove the four core, 8 GB target, and this run excludes remote model latency and coding quality.

packages

Small packages with one job each.

Swap behavior at the edges with Provider, Tool, ContextPolicy and RunStrategy. The engine keeps control of grants, budgets, validation and journaling, and a repository cannot grant itself a tool.

The main packages and what each is responsible for
Package Responsibility
ejm-harness Sessions, agent loop, providers, context, events, recovery
ejm-harness-exec Shared resource admission and command supervision
ejm-harness-auth Sign-in, verified identity, credential storage, and serialized renewal
ejm-harness-coding Native read, list, search, write, patch, and optional shell tools
ejm-harness-worker Persistent JSONL bridge for language SDKs
sdk/typescript Typed async API and TypeScript tool callbacks
sdk/python Sync and async Python API and tool callbacks
ejm-harness-bench Deterministic concurrency and command workloads

get it

Build ejm-harness from source.

The repository contains source packages. Registry releases and prebuilt worker binaries have not been published. It uses the pinned Rust toolchain and is MIT licensed. Persistent credentials require an OS key service; Linux builds also need D-Bus development headers. Read the host authentication guide.

Tests never call paid models.

Tests use replay fixtures. The terminal app built on the engine is ejm-cli, and the desktop app is ejm-ide. 

cargo build --release --workspace --locked
cargo test --workspace --locked

questions

Before you build on it.

Does it need an account or a server?

No. Neither ejm-harness nor ejm-cli requires a hosted workspace account or server.

Is native execution a sandbox?

No. It runs as the current user. The executor reports each restriction as enforced, monitored or unsupported, and rejects required protections that are unsupported before launch.

Which model providers work?

Chat Completions compatible streaming APIs, including DeepSeek endpoints, the Anthropic Messages API, native OpenAI Responses with an API key or ChatGPT sign-in, and the official Claude Code subscription adapter. The Claude route requires a separately installed official client and retains its managed provider policy.

Do I need Node or Python?

Only if you use that SDK. Rust hosts and ejm-cli have no Node or Python dependency.

See it in an app.

ejm-cli and ejm-ide are separate apps built on ejm-harness. Both are open source under the MIT license.
